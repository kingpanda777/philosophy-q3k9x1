**対象フィールドを増やす・変えるときは、そのフィールドを直接参照している箇所を

**理由。**2026年9月18日（`b89a515`）に追記へ `対象`（detail／explanation）を足したとき、
`applyAppends` だけを直して**書き込み前の事前検査 `auditKeyForms` を直し忘れた。**

**片側だけ直すと、次は書き込みの途中で止まりうる。**

## 使い方

```
node tools/add_batch.js <入力.json>            適用して検査まで走る
node tools/add_batch.js <入力.json> --dry-run  適用・検査したあと必ず差し戻す
```

**入力は1つの JSON にまとめる。**作問と追記と鍵語を別ファイルに分けない。

```json
{
  "作問": [ { "id":"q654", "philosophers":["リオタール"], "terms":["差異","言語"],
              "keys":["フィギュール"], "question":"…", "choices":["…","…","…","…"],
              "answer": 1, "explanation":"…", "detail":"…\n\n…\n\n…",
              "note":"…", "refs":["…"] } ],
  "追記": [ { "id":"q330", "find":"本文にある一文", "replace":"その一文＋足す文",
              "note_add":"追記の記録: …", "keys_add":["技術科学","非人間"] } ],
  "鍵語": {
    "作問由来": { "リオタール": [ {"語":"フィギュール","読み":"ふぃぎゅーる","追加":"…"} ] },
    "追記由来": { "リオタール": [ {"語":"技術科学","読み":"ぎじゅつかがく","追加":"…"} ] }
  }
}
```

**走る順序。どこかで落ちたら6ファイルを丸ごと元に戻して終了コード1で止まる**
（`questions.js` `keyterms.json` `index.html` `philosophers.js` `CLAUDE.md` `tools/keys_draft.json`）。

| 段 | 中身 |
|---|---|
| 0 | **入力の形を検査する。**1問も書かずに止まる |
| 1 | **鍵語の語形が本文に出るかを総点検する。**作問由来は草稿の本文、追記由来は追記後の本文で見る |
| 1.5 | **書き込みの前の検査7種。**keys 全部の語形・選択肢の長さ（「両者とも」「三者とも」型の下限を含む）・位置指し・detail の問題番号（作問と追記）・作問の detail の字数と段落数・`type` の指定・**作問の note の問題番号（存在しない問題を指していたら止める。人物の重ならない問題は △ を付けて一覧に出すだけ。2026年9月22日に足した）**。**2026年9月21日に規則と突き合わせて広げた。一覧は CLAUDE.md「入力の検査を規則と突き合わせた」の表。****`keys除去`・`refs追加`・`refs除去`・`refs置換` があるときは、それぞれの検査も走る。`type` の検査以外は作問に「許可」欄（理由）を書けば通る。`type` の検査だけは許可欄が無い**（2026年9月21日に足した） |

## 台帳モードを足した（2026年9月17日）

**点検の結果を台帳へ書き戻す作業も、毎回スクリプトを書き直していた。**
`fix.js` から `fix5.js`、`ledger6.js` まで6本。**そして書き直すたびに違う失敗をした。**
「十九世紀の反逆」の整備で**4回続けて止まった**ので、`tools/add_batch.js` へ吸収した。

```json
{
  "台帳": {
    "対象": ["人物", …],
    "刻印": "いつ何で判定したか",
    "扱い": {
      "主題": { "人物": ["語", …] },
      "理由": { "語": "なぜそう判じたか" }
    },
    "ずれの記録": { "語": "数えすぎ／数え漏らしの型" },
    "改名": { "人物": [ {"旧":"…","新":"…","読み":"…","理由":"…"} ] },
    "新規登録": { "人物": [ {"語":"…","読み":"…","付ける先":["qNNN"],"追加":"…"} ] }
  }
}
```

**台帳は作問・追記より先に走る。**改名で語形が変わると数え直しの対象も変わるためで、
**改名 → 扱いと数値 → 新規登録**の順に処理する。
**"作問" と "追記" を空にすれば、台帳だけを整えることもできる。**
**hits／全問は入力に書かない。**道具が本文を数えて実測を入れる。

**台帳モードには3つの操作がある**（2026年9月17日に足した）。
**「扱いの変更」**（旧の値を確かめてから書き換える）、
**「keysから外す」**（`q.keys`・`keys_draft` と、指定があれば台帳・`KEY_YOMI`・削除記録まで揃えて外す）、
改名の検査に**「部分文字列の残留を許す」**。

**先頭が重なる改名は、新語形を取り除いてから旧語形を探す。**
「通約不可能 → 通約不可能性」は旧語形が新語形の先頭部分なので、
**新語形が本文にある限り必ず残留と出る。**
**逃がし弁（`部分文字列の残留を許す`）は、別の語にたまたま旧語形が含まれる本来の型のために残してある。**

**鍵語を準備分として先に台帳へ登録した場合、入力の「鍵語」欄は使えない**（「既に台帳にある」で止まる）。
**そのときは `KEY_YOMI` への読みの追加を手で行う**
（`check_keys` の項目3が `q.keys` に出る語すべてに読みを要求するため）。

## 書き込みと差し戻しを、途中で止まっても壊れない形にした（2026年9月23日）

**何が起きたか。**grokipedia・goodreads の片づけの本番で、書き込みの途中に questions.js を開けずに落ち、
**差し戻しも同じファイルを開けずに落ちた**（`code: 'UNKNOWN'`、`errno: -4094`、`syscall: 'open'`）。
questions.js は途中まで書き換わったまま残り、残り5ファイルが戻ったかどうかも表示されなかった。
**手でバックアップから戻し、同じ入力で2回目を流して通した。**
1回目に最初に落ちた箇所のエラーは、ログの末尾しか残さなかったので分からない。

**原因の見立て。**`UNKNOWN`（-4094）は、libuv（Node のファイル操作の下の層）が名前を付けていない Windows のエラーである。
書き込みで開くときに出るのは、多くが `ERROR_USER_MAPPED_FILE`（1224。**別のプロセスがファイルをメモリに割り当てて開いている**）で、
エディタや、ウイルス対策・検索インデクサが**書き込み直後のファイルを読みに来た**ときに起きる。
**道具は同じ実行の中で questions.js を何度も書き直す**ので、その合間に当たりやすい。確定はしていない。

**直したこと。**読み書きの部品を `tools/_lib.js` の5番目（`readFileSafe`・`writeFileSafe`・`diagnose`）に置き、
add_batch.js と、add_batch から呼ばれる `gen_key_owner.js`・`progress_table.js` の書き込みをすべてこれに替えた
（`_lib.js` の `writeJson`・`readJson` もこれを使うので、それを読む他の道具にも及ぶ）。

|---|---|---|

## note を置き換え、unverified を外せるようにした（2026年9月23日）

**何が足りなかったか。**学派ごとの典拠の回（中世・近世の認識論）では、note の「確認できていない点:」を「解消済み:」に書き換え、
画面に出す `unverified` を外す作業が毎回あった。道具にこの経路が無く、**作業用の `tools/_work/note_edit.js` で行っていた。**
あわせて `refs追加` は、`refs` の欄そのものが無い問題で「refs の行が見つからない」と止まり、同じスクリプトで `refs: []` を先に作っていた。
**`note_edit.js` は使わないことにした。**

**足したもの。**入力は JSON ファイルで渡す。長い「含む」は、組み立て用のスクリプトファイル（`node file.js`）で本文から切り出して作る（`node -e` は使わない）。

```json
"note置換":       [ { "id": "q260", "含む": "確認できていない点: …。", "新": "解消済み: …。", "理由": "…" } ],
"unverified除去": [ { "id": "q278", "理由": "…" } ]
```

| 操作 | 歯止め（どれも許可欄なしに、1件も書かずに止める） |
|---|---|
| **note置換** | 「含む」が note の中で**ちょうど1回**当たること。「含む」が「確認できていない点:」を含むなら、「新」は**「解消済み:」で始まるか、「確認できていない点:」を残す**こと。「理由」は必須 |
| **unverified除去** | その問題に unverified があること。同じ問題を2回書かないこと |
| **書き終えたあと**（どちらかがあれば全ファイルを差し戻す） | **前向き**：unverified があるのに note に「確認できていない点:」が無い問題（全問）。**逆向き**：unverified を外したのに note に「確認できていない点:」が残っている問題 |

**記録の残し方。**note置換は、置き換えた文そのものが記録になるので、**note に何も書き足さない。**
代わりに**実行の最後に「コミットメッセージ用」として「id: 理由」を1問1行で出すので、それをコミットメッセージに載せる。**
unverified除去は、note の末尾に「画面の unverified を外した。理由: …」を書き足す。

**走る順序。**追記 → keys除去 → refs の除去と置換 → refs追加 → **note置換 → unverified除去** → 検査。
note置換を refs の操作より後に回すのは、refs の操作が note の末尾に書き足す記録と、置き換える文がぶつからないようにするため。

**`refs追加` の直し。**`refs` の欄が無い問題では、note の後ろ（source の閉じの手前）に欄を作って足す。追記の `refs_add` と同じ位置である。
